# ISSUES.md

## Обзор

Ниже приведены замечания и дефекты, выявленные при проверке соответствия проекта требованиям лабораторной работы по разработке документации, верификации требований и тестирования.

## 1. Отсутствует обязательный файл ISSUES.md

- Статус: High
- Описание: По условию задания необходимо зарегистрировать расхождения и дефекты в файле `ISSUES.md` в корне репозитория. Файл отсутствует.
- Последствие: нельзя формально подтвердить, что все выявленные несоответствия были зафиксированы и отслеживаются как дефекты.
- Рекомендация: добавить этот файл и хранить в нём все замечания по проекту, приоритеты и статус исправления.

## 2. В проекте отсутствуют сценарные тесты на переходы состояний сущности

- Статус: High
- Описание: В документации `docs/state-diagram.md` представлена диаграмма состояний для сущности "Прогноз валютной пары". Но в наборе тестов отсутствуют сценарные проверки последовательности операций, например: создание запроса -> сбор данных -> расчёт прогноза -> оценка качества -> публикация результата.
- Последствие: не подтверждена корректность переходов между состояниями и целостность жизненного цикла сущности.
- Рекомендация: добавить сценарные тесты по шаблону Arrange-Act-Assert для последовательных переходов между состояниями.

## 3. Отсутствуют HTTP-level заглушки для внешних сервисов в интеграционных тестах

- Статус: High
- Описание: В тестах используется мокирование методов/объектов, но не представлены заглушки на уровне HTTP-запросов к внешним сервисам (например, NBRB, Finnhub, сторонние источники данных).
- Последствие: интеграция с внешними системами не проверяется в условиях эмуляции реального HTTP-взаимодействия, что снижает достоверность проверки.
- Рекомендация: использовать `httpx.MockTransport`, `responses` или аналогичные инструменты для эмуляции внешних HTTP-вызовов.

## 4. Не подтверждено покрытие кода тестами не менее 70%

- Статус: High
- Описание: В проекте присутствует файл `forecasting/.coveragerc`, но нет подтверждённого отчёта о покрытии кода тестами с результатом >= 70%. Нет документа или артефакта, в котором указано фактическое значение покрытия.
- Последствие: нельзя подтвердить соответствие требованию по покрытию тестами.
- Рекомендация: запустить `pytest --cov` и зафиксировать отчёт (`coverage.xml` или HTML-отчёт) в репозитории/CI.

## 5. Не все требования, указанные в документации, поддерживаются в приложении явно

- Статус: Medium
- Описание: Документация описывает функциональность проекта достаточно широко, но часть требований остаётся «декларативной» без полной реализации в приложении: например полноценная пользовательская система, расширенные уведомления, персональные настройки, более широкий механизм fallback при сбоях внешнего API.
- Последствие: верификация требований частично опирается на предположение о наличии функциональности, а не на фактическую реализацию.
- Рекомендация: явно сопоставить каждый требованию с конкретным компонентом приложения и тестом.

## 6. Невыполнен этап сверки требований с реальным приложением в виде формализованных дефектов

- Статус: Medium
- Описание: В `docs/verification.md` есть проверка требований, но в используемом виде она не оформлена как полноценный список дефектов, назначенных и отслеживаемых в репозитории.
- Последствие: при наличии ошибок тяжело проводить контроль исправлений и отслеживание статусов.
- Рекомендация: добавить таблицу дефектов с колонками: ID, описание, приоритет, статус, ответственный, дата исправления.

## 7. Нет явной проверки граничных и отрицательных сценариев для ключевых API-методов

- Статус: Medium
- Описание: В текущих тестах есть отдельные проверки ошибок, но отсутствует системный набор негативных сценариев для некорректных значений, пустых данных, отсутствующих валютных пар, проблем с внешним API и недопустимых диапазонов параметров.
- Последствие: риски ошибок при реальном использовании остаются неподтверждёнными.
- Рекомендация: добавить параметризованные негативные тесты для каждого публичного endpoint и ключевого сервисного метода.

## 8. Не все требования имеют формально проверяемый способ проверки

- Статус: Medium
- Описание: Некоторые требования описаны достаточно общо и верифицируются в основном через экспертную оценку, а не через автоматизированный критерий.
- Последствие: повышается риск субъективной интерпретации требований.
- Рекомендация: переписать такие требования так, чтобы они имели измеримый и проверяемый критерий: конкретный ответ API, конкретный UI-элемент, конкретный порог времени, конкретный сценарий работы.

## 9. Требование к независимости тестов и их порядка запуска нужно дополнительно подтвердить

- Статус: Low
- Описание: Тесты в репозитории в целом выглядят локальными, но нет явных гарантий, что они полностью независимы от глобального состояния и порядка запуска.
- Последствие: возможна нестабильность при параллельном запуске или при изменении порядка тестов.
- Рекомендация: проверить fixtures, глобальные зависимости и состояние приложения, обеспечить изоляцию тестов.

## 10. Документ `frontend/README.md` является шаблоном Vite и не отражает проектно-специфическую документацию

- Статус: Low
- Описание: Внутри `frontend/README.md` сохранён стандартный шаблон React + Vite, а не документация по проекту или UI-компонентам.
- Последствие: документация по фронтенду не отражает реальные особенности приложения и может вводить в заблуждение.
- Рекомендация: заменить шаблон стандартной документацией проекта или добавить отдельный документ с описанием архитектуры фронтенда.

## Приоритеты исправления

1. Добавить `ISSUES.md` и вести список дефектов в репозитории.
2. Добавить сценарные тесты для жизненного цикла сущностей.
3. Добавить HTTP-mock тесты для внешних сервисов.
4. Подтвердить покрытие тестами не ниже 70%.
5. Уточнить требования, которые не имеют объективного способа проверки.

## Статус

Состояние на момент проверки: часть требований и документации выполнена, но формально проект не закрывает все пункты задания без дополняющих исправлений и оформления дефектов.
