# Карта выполнения заданий

Этот файл — навигация по материалам проекта для заданий 1 и 2. Он связывает каждый пункт задания с подтверждающим файлом и указывает, где требуется запуск приложения/тестов. Наличие документа или теста само по себе не подтверждает, что проверка была фактически выполнена: результаты запуска нужно фиксировать отдельно.

## Задание 1 — описание проекта, требования и верификация

### 1.1 Описание проекта в README

**Что показать:** назначение и целевых пользователей, стек технологий, архитектурную схему, модули и их обязанности, точки интеграции, инструкцию сборки и запуска.

**Материал:** [README.md](../README.md), разделы 1–6.

**Запуск приложения:** команды приведены в README. Основные команды из корня репозитория:

```bash
cd forecasting
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python -m uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

В другом терминале:

```bash
cd frontend
npm install
npm run dev
```

Перед демонстрацией проверь, что используемая версия Python совместима с закреплёнными зависимостями. В README указаны общие требования к среде; файл `forecasting/.python-version` проекта задаёт версию 3.11.9.

**Статус:** описание и Mermaid-диаграмма находятся в README. Фактический запуск нужно показать отдельно; README не является доказательством успешного запуска.

### 1.2 Спецификация требований

**Что показать:** бизнес-требования, не менее пяти пользовательских требований/use cases, не менее 15 функциональных и не менее 5 нефункциональных требований.

**Материал:** [docs/requirements.md](requirements.md).

**Замечание:** документ содержит BR, UC-01…UC-07, FR-01…FR-18 и NFR-01…NFR-06. Диаграмма use cases сейчас оформлена как Mermaid `flowchart`; если преподаватель требует именно UML use-case diagram, замени/дополни её стандартной UML-диаграммой с актором и use-case овалами.

**Команда запуска не требуется:** это документальная спецификация.

### 1.3 Верификация требований и регистрация дефектов

**Что показать:** способ проверки каждого требования, сверку с работающим приложением, исправленные формулировки непроверяемых требований и дефекты расхождений.

**Материалы:** [docs/verification.md](verification.md) и [ISSUES.md](../ISSUES.md).

**Команда запуска:** отдельной команды нет. Проверки интерфейса/API следует выполнять вручную или тестами, а фактические результаты и дефекты отражать в документах. В `verification.md` есть статусы, включая частичное соответствие; перед сдачей убедись, что каждый статус подтверждён реальной проверкой, а записи в ISSUES.md описывают найденные расхождения, а не только предположения.

### 1.4 Диаграмма состояний

**Что показать:** сущность с жизненным циклом, начальное и конечное состояния, события/условия переходов.

**Материал:** [docs/state-diagram.md](state-diagram.md).

**Команда запуска не требуется:** это диаграмма и её текстовое описание.

## Задание 2 — тесты и покрытие

### 2.1 Модульные, интеграционные и сценарные тесты

**Что показать:** тесты Arrange–Act–Assert, понятные имена, параметризацию, негативные случаи, независимость, моки и заглушки внешних HTTP-запросов.

**Материалы:** тесты в [`forecasting/tests/`](../forecasting/tests/), в частности:
- `test_rate_service.py`, `test_metrics_calc.py`, `test_pairs.py`, `test_technical.py` — модульные проверки;
- `test_api.py`, `test_routes_errors.py`, `test_sqlite_repository.py`, `test_nbrb_client.py` — API, репозиторий и интеграционные границы;
- `test_scenario_and_integration.py` — последовательности сценариев;
- `test_forecaster.py`, `test_macro_service.py`, `test_bank_rates_service.py` и `test_coverage_boost.py` — дополнительные проверки модулей и граничных случаев.

Уточни по содержимому конкретных тестов, что внешние вызовы действительно заменены моками/заглушками и тесты не обращаются к реальным сервисам.

**Запуск из каталога `forecasting`** (после установки `requirements-dev.txt` в виртуальное окружение):

```bash
python -m pytest -q
```

Сохрани фактический вывод прогона для демонстрации; не указывай заранее ожидаемое количество тестов.

### 2.2 Измерение тестового покрытия, минимум 70%

**Инструмент:** pytest-cov указан в [forecasting/requirements-dev.txt](../forecasting/requirements-dev.txt).

**Запуск из каталога `forecasting`:**

```bash
python -m pytest \
  --cov=api \
  --cov=service \
  --cov=domain \
  --cov=infrastructure \
  --cov=main \
  --cov-report=term-missing \
  --cov-report=html \
  --cov-fail-under=70
```

HTML-отчёт создаётся в `forecasting/htmlcov/` (локальный артефакт; обычно его не добавляют в Git).

**Статус проверки:** последний предоставленный вывод тестового прогона показал 37 passed. Последний предоставленный coverage-отчёт до добавления дополнительных coverage-тестов показал 45.71% и не достиг порога. В GitHub сейчас есть последующий коммит с дополнительными тестами (`implement tests for 70%`), но результат покрытия после этого коммита здесь не подтверждён. Запусти приведённую команду на актуальной версии проекта и сохрани новый вывод; считать пункт выполненным можно только если итог не ниже 70% и команда завершается успешно.
