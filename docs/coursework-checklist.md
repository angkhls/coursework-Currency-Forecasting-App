# Карта выполнения заданий

Этот файл — оглавление материалов по заданиям 1–3. Ссылки ведут к описаниям и артефактам проекта. Документ, тест-кейс или шаблон отчёта сами по себе не подтверждают фактическое выполнение проверки: реальные результаты и доказательства необходимо фиксировать отдельно.

## Задание 1 — описание проекта, требования и верификация

### 1.1 Описание проекта

**Что показать:** назначение проекта, целевых пользователей, стек технологий, архитектурную схему, модули, интеграции и инструкции сборки/запуска.

**Материал:** [README.md](../README.md), разделы 1–6.

**Запуск backend** (из корня репозитория):

```bash
cd forecasting
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

**Запуск frontend** в другом терминале:

```bash
cd frontend
npm install
npm run dev
```

Открой адрес, напечатанный Vite в терминале (по текущей конфигурации — `http://localhost:3000/`). Перед демонстрацией проверь версии Python/Node и наличие необходимых переменных окружения.

### 1.2 Спецификация требований

**Что показать:** бизнес-требования, пользовательские сценарии, не менее 15 функциональных и не менее 5 нефункциональных требований.

**Материал:** [docs/requirements.md](requirements.md). В документе приведены BR, UC-01…UC-07, FR-01…FR-18 и NFR-01…NFR-06. Диаграмма пользовательских сценариев сейчас оформлена Mermaid `flowchart`; если требуется именно UML use-case diagram, её нужно дополнить/заменить UML-диаграммой.

**Запуск не требуется:** это документальная спецификация.

### 1.3 Верификация требований и дефекты

**Что показать:** способ проверки требований, сверку с приложением, известные расхождения и их фиксацию.

**Материалы:** [docs/verification.md](verification.md), [ISSUES.md](../ISSUES.md).

**Важно:** проверь, что статусы верификации основаны на реально выполненных проверках и дефекты описаны фактическими наблюдениями.

### 1.4 Диаграмма состояний

**Что показать:** сущность с жизненным циклом, состояния, события и условия переходов.

**Материал:** [docs/state-diagram.md](state-diagram.md). Отдельная команда запуска не требуется.

## Задание 2 — тесты и покрытие кода

### 2.1 Модульные, интеграционные и сценарные тесты

**Что показать:** Arrange–Act–Assert, понятные названия, негативные случаи, независимость тестов и моки/заглушки внешних зависимостей.

**Материалы:** [`forecasting/tests/`](../forecasting/tests/), в том числе `test_rate_service.py`, `test_metrics_calc.py`, `test_pairs.py`, `test_technical.py`, `test_api.py`, `test_routes_errors.py`, `test_sqlite_repository.py`, `test_nbrb_client.py`, `test_scenario_and_integration.py`.

**Запуск из каталога `forecasting`** после установки `requirements-dev.txt`:

```bash
python -m pytest -q
```

Сохрани реальный вывод команды и проверяй, что тесты не зависят от недоступных внешних сервисов.

### 2.2 Покрытие кода не менее 70%

**Инструмент:** `pytest-cov` в [forecasting/requirements-dev.txt](../forecasting/requirements-dev.txt).

**Запуск из каталога `forecasting`:**

```bash
python -m pytest \
  --cov=api \
  --cov=service \
  --cov=domain \
  --cov=infrastructure \
  --cov=main \
  --cov-report=term-missing \
  --cov-report=html \
  --cov-fail-under=70
```

HTML-отчёт создаётся в `forecasting/htmlcov/`. Задание считается подтверждённым только после успешного актуального прогона с итогом не ниже 70%; старые результаты не заменяют новый отчёт.

## Задание 3 — планирование и выполнение тестирования

### 3.1 План тестирования

**Что требуется:** цель, области тестирования и исключения со ссылками на FR/NFR, стратегия и инструменты, критерии начала/приостановки/возобновления/завершения, метрики и формулы.

**Материал:** [docs/test-plan.md](test-plan.md).

**Статус:** план подготовлен документально. Фактическое выполнение проверок отражается в отчёте 3.4.

### 3.2 Чек-лист функциональных требований

**Что требуется:** все FR, сгруппированные по модулям, с позитивной и негативной проверкой для каждого требования.

**Материал:** [docs/test-checklist.md](test-checklist.md).

**��татус:** чек-лист подготовлен; отметки о выполнении ставь только после реальных проверок.

### 3.3 Тест-кейсы

**Что требуется:** не менее 25 тест-кейсов, покрывающих все FR высокого приоритета. В каждом кейсе нужны ID, приоритет, связанное требование, модуль, заголовок, исходные данные, шаги и ожидаемый результат.

**Материал:** [docs/test-cases.md](test-cases.md) — 32 тест-кейса с матрицей связей с FR-01…FR-18.

**Статус:** набор кейсов подготовлен. Это описание проверок, а не свидетельство их фактического выполнения.

### 3.4 Выполнение тест-кейсов и доказательства

**Что требуется:** реально пройти кейсы, записать фактический результат и статус (`Pass`, `Fail`, `Blocked`), приложить скриншоты и/или видео. Для `Fail` указать отклонение от ожидаемого результата; невыполненные проверки не отмечать `Pass`.

**Материал для результатов:** [docs/test-execution.md](test-execution.md).

**Доказательства:** сохраняй изображения/видео в `docs/test-evidence/`, называя файлы по ID кейса, например `TC-01-dashboard.png`, и добавляй относительные ссылки на них в отчёт выполнения.

**Запуск приложения:** команды приведены выше и в [README.md](../README.md). Backend и frontend запускаются в отдельных терминалах. Для API-проверок можно пользоваться Swagger UI по адресу `http://localhost:8000/docs`; адрес должен быть доступен при работающем backend.

**Статус:** выполнение не подтверждено одним только наличием шаблона. Заполни отчёт и добавь реальные доказательства.

### 3.5 Описание найденных дефектов

**Что требуется:** для каждого фактически найденного дефекта привести краткое и подробное описание, ожидаемый/фактический результат, FR, шаги воспроизведения, воспроизводимость, важность и срочность, симптом и обходной путь.

**Материал:** [docs/test-defects.md](test-defects.md) — создай/заполни по фактическим результатам тестирования. [ISSUES.md](../ISSUES.md) содержит ранее зарегистрированные замечания и не заменяет автоматически отчёт о дефектах, найденных при выполнении кейсов задания 3.4.

Если дефектов не найдено, зафиксируй, что дефекты не обнаружены в выполненном объёме тестирования, укажи список/количество реально выполненных кейсов и ограничения проверки. Не придумывай дефекты и результаты.
