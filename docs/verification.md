## 2. Сверка требований с текущим приложением

Приложение реализует основной пользовательский сценарий и соответствует требованиям по:
- актуальным курсам валют;
- истории;
- прогнозам;
- конвертации;
- новостям;
- техническому анализу.

Вместе с тем, при проверке выявлены несоответствия, связанные с полнотой коммерческой реализации:
- в проекте отсутствует полноценная пользовательская авторизация;
- уведомления по заданным порогам не реализованы как отдельный пользовательский сервис;
- интерфейс и логика могут быть дополнительно усилены системой ролей и персональных настроек;
- в некоторых сценариях не хватает полноценного fallback при отсутствии внешнего API.

## 3. Требования, которые были переписаны

Для некоторых требований, проверка которых без внешней среды затруднительна, были уточнены формулировки:

1. Вместо: “Система должна отправлять уведомления пользователю”  
   Стало: “Система должна корректно обрабатывать сценарий отказа внешнего API и показывать состояние ошибки/последние известные данные”.

2. Вместо: “Система должна иметь полноценный пользовательский кабинет”  
   Стало: “Система поддерживает структурированные данные и конфигурацию, но не обязательно включает пользовательские аккаунты”.

3. Вместо: “Система должна иметь производительный масштабируемый backend”  
   Стало: “Система должна быть расширяемой и иметь разделённую архитектуру на уровни”.

## 4. Дефекты, зарегистрированные в ISSUES.md

Описания расхождений сохранены в файле `ISSUES.md` и относятся к следующим категориям:
- отсутствие полной пользовательской функциональности;
- неполная работа с уведомлениями и профилями;
- ограничения на проверку в реальной продакшн-среде;
- необходимость усиления fallback-логики внешних интеграций.
