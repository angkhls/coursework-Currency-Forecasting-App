# План тестирования — Currency Forecasting App

> Документ описывает план проверок для задания 3. Он определяет области, стратегию и критерии; сам по себе не подтверждает, что тесты уже выполнены. Фактические результаты, статусы и доказательства следует заносить в `test-execution.md` после выполнения проверок.

## 1. Цель тестирования

Проверить, что основные пользовательские сценарии Currency Forecasting App и требования из [спецификации](requirements.md) реализованы корректно, включая получение и отображение курсов, историю, графики, прогнозирование, технические индикаторы, конвертацию, новости, API и обработку ошибок. Выявить и зафиксировать воспроизводимые дефекты до сдачи проекта.

Тестирование охватывает как функциональное поведение, так и выбранные нефункциональные характеристики. Оно не является сертификацией безопасности, производительности в промышленной среде или доступности внешних поставщиков данных.

## 2. Объект тестирования и тестовая среда

**Объект:** веб-приложение с React/Vite frontend и FastAPI backend, слоями service/domain/infrastructure, локальным хранилищем SQLite и интеграциями с внешними источниками (включая НБРБ и Finnhub).

**Основные части системы:**
- API: `forecasting/api/`;
- бизнес-логика: `forecasting/service/`;
- доменные модели: `forecasting/domain/`;
- адаптеры и хранилища: `forecasting/infrastructure/`;
- интерфейс: `frontend/src/`;
- существующие backend-тесты: `forecasting/tests/`.

**Среда:** локал��ная машина разработчика, изолированное Python virtualenv и Node.js/npm; тестовая база/временное хранилище для проверок. Во время автоматических тестов внешние HTTP-сервисы должны заменяться моками или HTTP-заглушками, чтобы результат не зависел от сети, ключей и состояния внешних систем. Реальные внешние интеграции можно проверять отдельно как ручную smoke-проверку, если они доступны.

Фактические ОС, версии Python/Node, commit SHA, браузер и адреса запущенных сервисов фиксируются в отчёте выполнения, а не предполагаются заранее.

### 3.2 Вне области или ограничено

| Область | Причина исключения/ограничения |

| Авторизация, роли, пользовательские профили и персональные уведомления | Такие функции не заявлены как реализованные в текущем объёме продукта; их нельзя считать проверяемой функциональностью без изменения требований/реализации. Соответствующие замечания следует сверить с `ISSUES.md`. |

| Нагрузочная/стрессовая проверка промышленного уровня и длительный soak-тест | Требуют согласованной целевой нагрузки, отдельного окружения и стабильных тестовых данных. Допускается локальный ограниченный эксперимент; его нельзя выдавать за production performance evidence. |

| Проверка реальной PostgreSQL-инфраструктуры | Не входит в обязательный локальный прогон, если PostgreSQL-среда/контейнер не подняты. SQLite-проверки выполняются отдельно; отсутствие PostgreSQL следует отразить как ограничение, а не как успешный результат. |
| Аудит безопасности, penetration testing и юридическая/финансовая точность прогноза | Не являются целью функционального плана и требуют отдельной методики и компетенций. Базовые проверки валидации входных данных остаются в области тестирования. |

Если исключённая область прямо включена преподавателем в обязательный scope, её нужно вернуть в план и выполнить либо указать обоснованный статус Blocked.

## 4. Тестовая стратегия

### 4.1 Уровни

1. **Модульный/unit:** функции расчёта метрик, индикаторов, валютных пар и логика отдельных сервисов. Зависимости заменяются моками; тесты следуют Arrange–Act–Assert и изолированы друг от друга.
2. **Интеграционный:** взаимодействие API с сервисами, SQLite-репозитория с БД и клиентских адаптеров с HTTP-заглушками. Проверять сериализацию, валидацию и ожидаемые ошибки на границах компонентов.
3. **Сценарный/API:** последовательности пользовательских операций через несколько методов/endpoint-ов, включая чтение курса, конвертацию, историю и сценарии прогноза. Использовать `httpx`/`AsyncClient` и тестовые зависимости.
4. **Системный ручной:** запуск frontend и backend, проверка основных пользовательских потоков в приложении и поведения ошибок.
5. **UI/browser:** проверка визуальных состояний и основных потоков в браузере; Playwright предусмотрен npm scripts проекта (`npm run e2e`, при наличии тестов и настроенной среды). Скриншоты/видео сохранять как доказательства.
6. **Нагрузочный/performance:** ограниченная проверка стандартных endpoint-ов через Locust, если подготовлены тестовая среда и сценарий. Измерять latency и ошибки, не направлять нагрузку на production или публичные сторонние API.

### 4.2 Виды проверок

- позитивные, негативные и граничные проверки;
- регрессионные проверки;
- проверка интеграционных контрактов и обработки ошибок;
- ручная проверка UI, браузера и responsive layout;
- базовые performance-проверки NFR-01;
- проверка отказа/таймаута интеграции посредством заглушек.

### 4.3 Инструменты и команды

- Python `pytest`, `pytest-asyncio`, `pytest-cov`, `httpx`/`AsyncClient` — backend и API;
- `unittest.mock`/`AsyncMock` и `httpx.MockTransport` либо эквивалент — моки и HTTP-заглушки;
- Vitest — frontend unit/component-тесты (`cd frontend && npm test`);
- Playwright — UI/e2e при наличии тестов и установленного browser runtime (`cd frontend && npm run e2e`);
- Locust — ограниченная нагрузочная проверка (`cd forecasting && source .venv/bin/activate && locust -f locustfile.py`; выполнять только если файл сценария существует и тестовая цель запущена);
- браузерные DevTools и скриншоты/запись экрана — ручные UI-доказательства;
- Markdown-отчёты в `docs/` — план, чек-лист, тест-кейсы, результаты и дефекты.

Backend команды запускаются из `forecasting` внутри активного venv. Frontend команды — из `frontend`. Любая команда, не применимая к текущей конфигурации, фиксируется как Blocked с причиной; наличие npm script или зависимости само по себе не означает, что соответствующий тест реально настроен/выполнен.

## 5. Приоритеты требований

Приоритеты устанавливаются для планирования тест-кейсов, это не изменение спецификации:

- **Высокий:** FR-01, FR-03, FR-05, FR-11, FR-12, FR-13, FR-15, FR-16. Это базовые пользовательские потоки, критичные данные и API/error handling.
- **Средний:** FR-02, FR-04, FR-06, FR-07, FR-08, FR-09, FR-10, FR-14, FR-18.
- **Средний/инфраструктурный:** FR-17; проверяется локальный запуск обязательно, Docker при доступности среды.
- NFR-01…NFR-06 оцениваются по соответствующим проверкам из раздела 3, а не как функциональные FR.

Изменение приоритета допускается с обоснованием в этом документе и должно быть согласовано с преподавателем/владельцем требований.

## 6. Метрики и формулы

Метрики рассчитываются по зарегистрированным тест-кейсам и фактически заведённым дефектам. Все знаменатели и статусы должны быть явно указаны в отчёте.

1. **Процент успешного прохождения тест-кейсов**

   `Pass rate = количество кейсов со статусом Pass / количество выполненных кейсов (Pass + Fail) × 100%`

   Blocked и Not Run не включаются в знаменатель успешности, но показываются отдельно.

2. **Процент выполнения тест-кейсов**

   `Execution rate = количество выполненных кейсов (Pass + Fail) / общее количество запланированных кейсов × 100%`

   Blocked показываются отдельно и не считаются выполненными.

3. **Покрытие функциональных требований тест-кейсами**

   `Requirements coverage = число FR, имеющих хотя бы один связанный тест-кейс / общее число FR в спецификации × 100%`

   Полное покрытие FR означает, что в `test-cases.md` есть связь с каждым FR-01…FR-18; для каждого требования чек-лист также содержит позитивную и негативную проверку.

4. **Процент устранения дефектов по важности**

   `Defect resolution rate (severity) = число исправленных дефектов данной важности / общее число найденных дефектов данной важности × 100%`

   Рассчитывать отдельно для Blocker/Critical/High/Medium/Low (или согласованной шкалы). Для знаменателя 0 писать `N/A (дефектов данной важности не найдено)`, а не 100%.

5. **Покрытие кода** — отдельная метрика задания 2, не замена покрытия требований:

   `Code coverage = выполненные исполняемые строки / общее число учитываемых исполняемых строк × 100%`.

   Целевое значение проекта по заданию 2 — не менее 70% согласно принятой конфигурации исключений. В отчёте задания 3 указывать только новый фактический вывод pytest-cov с командой и commit SHA; прежнее или неподтверждённое значение не переносить.

## 7. Критерии тестирования

### 7.1 Критерии начала (Entry criteria)

Тестирование можно начинать, к��гда:
- тестируемый commit зафиксирован и доступен;
- зависимости backend/frontend установлены в изолированных окружениях;
- приложение запускается либо для не требующих сервера unit-тестов подготовлена изолированная среда;
- определены тестовые данные, настройки и заглушки внешних сервисов;
- чек-лист и кейсы имеют ID, связи с FR и ожидаемые результаты;
- нет известного Blocker, делающего весь тестируемый контур недоступным.

Если часть условий не выполнена, соответствующие проверки не стартуют и получают `Blocked` с объяснением.

### 7.2 Критерии приостановки (Suspension criteria)

Приостановить затронутый набор проверок, если:
- backend или frontend не запускается и основной сценарий недоступен;
- тестовая БД повреждена/недоступна или тестовые данные неконсистентны;
- обнаружен Blocker/Critical, делающий дальнейшие результаты недостоверными;
- тесты зависят от недоступного внешнего сервиса и для него нет заглушки;
- доля ошибок тестового окружения превышает 20% попыток в прогоне.

Зафиксировать причину, затронутые кейсы, окружение и известные дефекты. Незатронутые независимые unit-тесты могут продолжаться.

### 7.3 Критерии возобновления (Resumption criteria)

Возобновить проверки после устранения блокирующей причины, подтверждения корректности окружения и тестовых данных, повторного smoke-теста и фиксации нового commit/build. Кейсы, которые могли быть затронуты исправлением, выполнить повторно; результаты прежнего build не переносить на новый.

### 7.4 Критерии завершения/приёмки (Exit/acceptance criteria)

План считается успешно завершённым, когда одновременно:
- выполнено 100% кейсов высокого приоритета; все остальные кейсы выполнены либо имеют согласованный и объяснённый Blocked/Not Run статус;
- `Execution rate` не ниже 95%; оставшиеся неисполненные кейсы перечислены с причиной;
- `Pass rate` не ниже 95% по выполненным кейсам, и 100% высокоприоритетных кейсов имеют Pass;
- покрытие требований тест-кейсами — 100% FR-01…FR-18, а в чек-листе для каждого FR есть позитивная и негативная проверки;
- нет открытых Blocker/Critical дефектов; открытые High дефекты либо исправлены и перепроверены, либо имеют согласованное решение/обходной путь и явно отражены в итоговом отчёте;
- по каждой важности дефекта указано число найденных и исправленных дефектов и рассчитан процент устранения (либо N/A при нулевом количестве);
- результаты NFR-проверок содержат измерения/доказательства или явно обозначены как Blocked/не проверенные;
- автоматический backend-тестовый набор проходит; code coverage не ниже 70% подтверждён актуальным отчётом pytest-cov, если он входит в сдаваемый набор работ.

В случае невыполнения любого порога выпускной статус — `Не пройдено` или `Пройдено с ограничениями`, с перечислением отклонений и их согласования. Нельзя считать Blocked проверку успешной.

## 8. Приостановки, риски и допущения

Основные риски: изменение внешних API, отсутствие токенов/интернета, нестабильность тестовых данных, различия часовых поясов/текущей даты, нехватка браузерных runtime и отличие локальной среды от production. Снижать риск детерминированными фикстурами, моками, HTTP-заглушками, фиксацией версии/commit и записью полного окружения.

Результаты ручного и автоматического тестирования должны быть трассируемы к ID тест-кейса и FR. Скриншоты/видео для реально выполненных UI-кейсов хранить в `docs/test-evidence/` и ссылаться на них в отчёте выполнения. Не создавать фиктивные результаты или доказательства.
